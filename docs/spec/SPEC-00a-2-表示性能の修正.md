## 目的

SPEC-00a の計測では、基準2（スクロールで白く抜けない）と基準3（A1 を 400% に拡大して 0.5 秒以内に鮮明になる）が大きく未達だった。

| 処理 | A4（スキャン風） | A1（線分 15 万本） |

したがって、**小さなタイルを何枚も描く方式は極めて非効率**である。400% で見える範囲に 20 枚のタイルを描くと、約 3.4 秒分の処理になる。同じ範囲を1回で描けば、約 0.22 秒で済む。

### コードの問題

1. **同じ描画要求が重複して出され、結果が捨てられている**
   - `Viewer.tsx` の低解像度の先読みは、スクロールのたびに再実行され、同じページの要求を何度も出す。
   - `PageView.tsx` は、`visible` や `generation` が変わるたびに要求を出し直す。
   - どちらも、クリーンアップで `active = false` になると、届いた結果を `close()` で**キャッシュせずに捨てる**。
   - このため、スクロール中はほぼ何もキャッシュに残らない。
2. **画面外へ出た要求が取り消されない**。取り消すのは倍率を変えたときだけなので、古い要求が新しく見えている要求より先に処理される。
3. **タイルの計算の誤り**（`PageView.tsx` の `tiles`）
   - 右端に `pageLeft` を引いていない。
   - 下端に `layout.top` を引いていない。
   - このため、ページが画面の途中から始まる場合や横にずれている場合に、不要なタイルを要求する。
4. **Worker ごとに同じページの DisplayList を作っている**。タイルを最も空いている Worker へ振り分けるため、重いページの DisplayList（約 0.4 秒）を複数の Worker で作ることになる。
5. **試験用 PDF が現実的でない**
   - 96MB のうち 35MB は、内容と関係のないパディング（`KaruPdfBenchmarkPadding`）である。
   - A4 の 250 ページは、1つの画像オブジェクトを共有している（MuPDF が同じ画像をまとめたため）。
   - そのため、JPEG の展開が1回しか起きず、スキャンのページが実際より軽く見える。
6. **計測の誤り**
   - `blank-frames` は、DOM がまだないページを数えていない。
   - 横スクロール後の鮮明化の時間を Playwright の `expect.poll` の間隔で測っているため、100〜1000ms 刻みの粗い値になる。
   - `zoom-settle` は、新しい要求が出る前に終了と判定されることがある。

## 変更内容

### 1. 描画要求の管理（新規 `src/client/RenderScheduler.ts`）

main thread に、描画要求を一元管理する `RenderScheduler` を置く。**PageView と Viewer は、`PdfWorkerPool.render` を直接呼ばない。**

```ts
type Priority = 0 | 1 | 2 | 3   // 0: 見えている / 1: 進行方向の先読み / 2: 逆方向の先読み / 3: 空き時間の下準備
interface RenderParams { pageIndex: number; renderScale: number; deviceRect: DeviceRect | null }
want(key: string, params: RenderParams, priority: Priority, onReady: (bitmap: ImageBitmap) => void): () => void  // 戻り値は release
has(key: string): boolean
```

- **キャッシュにある場合**: `onReady` を呼ぶ。release では何もしない。
- **同じ key の要求が処理中の場合**: 待ち手に加える。
  - 新しい優先度のほうが高ければ（数値が小さければ）、Worker へ `reprioritize` を送る。
- **それ以外の場合**: Worker へ `render` を送る。
- **結果が届いたとき**: 待ち手が 0 人でも、**必ず BitmapCache に入れる**。その後、残っている待ち手へ通知する。**届いた結果を捨ててはならない。**
- **release**: 待ち手から外す。
  - 待ち手が 0 人になり、まだ Worker で処理が始まっていなければ、`cancelJobs` で取り消す。
  - 処理がすでに始まっていれば、そのまま完了させてキャッシュする。
- `pendingCount()`（処理待ちと処理中の件数）を提供し、`isIdle` に使う。

### 2. Worker の通信（`protocol.ts`、`pdf.worker.ts`、`PdfWorkerPool.ts`）

- `generation` と `cancelBelow` を廃止し、次の2つに置き換える。
  - `cancelJobs {jobIds}`: キューにある指定の要求を捨て、`{jobId, cancelled: true}` を返す。
  - `reprioritize {jobId, priority}`: キューにある要求の優先度を変えて、並べ直す。
- **ページの担当 Worker を固定する**: `pageIndex % workerCount` の Worker が、そのページのすべての要求（全体の描画と詳細の描画）を処理する。こうすると、DisplayList は1ページにつき1つの Worker にしかできない。
- キューの並び順は、優先度 → 受け付け順。
- `render.ts` と `pdf.worker.ts` で画素列を二重にコピーしているので、1回にする。
- `DisplayListCache` の上限を、件数ではなく推定バイト数にする。
  - MuPDF.js から DisplayList のサイズが取れない場合は、生成時間を代わりの目安にしてよい（重いページほど大きい）。
  - 上限は Worker 1本あたり 12 ページ相当を目安にし、根拠を報告すること。

### 3. 高倍率の詳細描画（タイル方式から置き換え。新規 `src/viewer/detailRegion.ts`）

- ページをデバイス px にしたときの長辺が 2048 以下なら、今までどおり、ページ全体を現在の倍率で描いたプレビューだけで表示する。
- 長辺が 2048 を超える場合:
  - 長辺を 2048 に抑えたプレビューを下地にする。
  - その上に、**詳細領域を1枚だけ**重ねる。詳細領域は、ページのうち見えている部分を、上下左右に 256 デバイス px ずつ広げた範囲（ページの外は切り落とす）。
- 詳細領域の座標は 128 デバイス px 単位に丸める（再利用しやすくするため）。キャッシュの key は `${pageIndex}:${scale}:detail:${x0},${y0},${x1},${y1}`。
- `detailRegion.ts` には、次の純関数を置く。
  - `visiblePartOfPage(pageBox, viewport)`: ページが画面の途中から始まる場合や、横にずれている場合を正しく扱うこと。
  - `computeDetailRegion(visible, pageDeviceSize, margin=256, grid=128)`
  - `regionCovers(region, visible)`
- **スクロールしたとき**
  - 見えている部分が今の詳細領域に収まっている間は、何もしない。
  - はみ出したら、スクロールが 100ms 止まった時点で新しい詳細領域を要求する。
  - 新しい領域が届くまで、古い詳細領域を元の位置のまま表示し続ける。
- **倍率を変えたとき**: 古い詳細領域をすぐ隠し、プレビューを CSS で拡大縮小して表示する。新しい倍率の詳細領域が届いたら差し替える。
- 詳細の描画は、担当 Worker に1回の描画として依頼する（分割しない）。

### 4. 先読みと仮想化（`Viewer.tsx`、`PageView.tsx`）

- `PageView` は、DOM がある間、自分の低解像度版とプレビューを `want` する。
  - 優先度は、見えていれば 0、それ以外なら 1 または 2。
  - 見え方が変わったら、要求を出し直さずに優先度だけを変える。同じ key の `want` を取り直せば、scheduler が重複を除いて優先度を上げる。
  - アンマウントされたら release する。
- **Viewer の先読み**
  - スクロールの向きを覚えておく。
  - 進行方向の3画面分と、逆方向の1画面分にあるページについて、低解像度版（長辺 512px）を `want` する。優先度は、進行方向が 1、逆方向が 2。
  - 先読みの対象は、前回との差分で `want` と release をする。**スクロールのたびに全部を出し直してはならない。**
- **空き時間の下準備**（`?warm=1` のときだけ有効にする実験機能）
  - Worker が空いているとき、現在のページから近い順に、全ページの長辺 256px の版を優先度 3 で描く。
  - 別の BitmapCache（上限 64MB）に入れ、どのページも少なくとも粗い版を表示できるようにする。
  - 効果は計測で判断する（第7章）。
- **白く抜けたフレームの判定を直す**
  - スクロール中は、requestAnimationFrame ごとに、`layout` と `scroller.scrollTop` の実際の値から、見えているページを求める。
  - そのページの DOM がないか、`data-has-bitmap` が `'true'` でなければ、白く抜けたフレームとして数える。

### 5. 鮮明さの追跡と計測

- Viewer に `isSharp()` を用意する。見えているすべてのページについて、次の条件を満たすとき true を返す。
  - 詳細描画を使わないページ: 現在の倍率のプレビューが描かれている。
  - 詳細描画を使うページ: 見えている部分を覆う、現在の倍率の詳細領域が描かれている。
- 計測する区間:
  - `open`: ファイルを選んでから、1ページ目に何かが（低解像度でもよい）描かれるまで。今までどおり。
  - `open-sharp`（新規）: ファイルを選んでから、1ページ目が鮮明になるまで。
  - `zoom-settle`: 倍率の確定から、`isSharp()` が true になるまで。確定した時点で、見えているページのどれか1つでも鮮明でなければ、計測中とみなす。
  - `pan-settle`（新規。ページ内で測る）: 高倍率でスクロールが 100ms 止まってから、`isSharp()` が true になるまで。
- `window.__karu` に `isSharp()` を追加する。

- 合計サイズは、画像の解像度・品質・ノイズの量で 90〜130MB に調整する。
- A1 のページは今の内容のままにする（線分 15 万本の「重い図面」の代表とする）。
- **新規 `scripts/engine-bench.mjs`**
  - 上記の Claude Code の測定スクリプトを元に、`test-data/heavy-300p.pdf` について、ページの種類ごとに次を表で表示する。
    - DisplayList の生成時間
    - 低解像度、幅に合わせた全体、400% の詳細領域（1952×1412px）それぞれの描画時間
  - `package.json` に `"engine-bench": "node scripts/engine-bench.mjs"` を追加する。

### 7. ベンチマーク（`e2e/perf.spec.ts`）

Worker 1〜3 本のそれぞれで、次を計測する。`?warm=1` なしと `?warm=1` ありの両方で行う。

1. **開く**: `open` と `open-sharp`（3回の中央値）
2. **スクロール**（「幅に合わせる」の状態）
   - 開いた直後の、まだキャッシュがない状態で、毎秒約 1500 CSS px と毎秒約 3000 CSS px の2通りで、それぞれ5秒ずつ下へスクロールする。
   - 同じ区間をもう一度スクロールする（キャッシュがある状態）。
   - それぞれについて、白抜けの割合と、最も長く続いた白抜けの時間を取る。
3. **拡大**
   - A1 のページ（6ページ目）を画面に表示して `isSharp()` を待つ。
   - `setZoom(4)` を実行して `zoom-settle` を取る。
   - 500 CSS px 横へスクロールして `pan-settle` を取る。
   - 1500 CSS px 横へスクロールして `pan-settle` を取る。
   - 同じことを A4 のスキャン風ページ（1ページ目）でも行う。
4. 描画時間の平均と p95（Worker 側）、Worker ごとの処理件数

結果は今までどおり JSON とコンソールの表に出す。

**開発機（Ryzen 5 5625U）での目標**: 利用者のPCはもっと遅い想定なので、合格基準より厳しくする。
