# SPEC-00a-3: 試作（拡大時の描画順序の修正）

## 実行モデル指定（必須）

- モデル: `gpt-5.6-sol`
- reasoning effort: `high`
- 選定理由: SPEC-00a-2 の続きで、同じスレッドで表示の中核ロジックを直すため（sol-high で始めた案件を途中で降格しない）

---

## 目的

SPEC-00a-2 の計測では、A1 を 400% に拡大してから鮮明になるまでに 2.9〜7.5 秒かかった（目標は 0.3 秒、合格基準は 0.5 秒）。

レビューで、主な原因が描画の順序にあることが分かった。この SPEC ではそれを直す。あわせて、横スクロールしたときの再描画を減らす。

## 原因（レビューで判明）

`src/viewer/PageView.tsx` では、次の順で処理が起きている。

1. 400% では `usesDetail` が true になり、`previewScale` が「長辺 2048px」のスケールに変わる。
2. そのため、`previewKey` が変わり、**A1 ページ全体の描画（重いページでは 1.4〜2.5 秒）** が優先度 `props.priority`（見えていれば 0）で要求される。
3. この要求は、詳細領域の要求より先に、**同じ担当 Worker** へ入る。
4. その結果、詳細領域の描画（約 0.3〜0.4 秒）が、このページ全体の描画を待つことになる。

## 対象

- 変更してよいファイル: `src/viewer/PageView.tsx`、`src/viewer/Viewer.tsx`、`src/viewer/detailRegion.ts`、`tests/detailRegion.test.ts`、`e2e/perf.spec.ts`
- 上記以外は変更しない。

## 変更内容

### 1. 詳細描画を使うときは、下地の描き直しを後回しにする

- `usesDetail` が true のときは、下地（`preview-canvas`）に**すでに描かれている画像をそのまま CSS で拡大して使う**。スケールは問わない（低解像度版でもよい）。
- 長辺 2048px の下地は、**詳細領域が描かれて `sharp` になった後に、優先度 2 で**要求する。
  - それまでは `want` しない。
  - 届いたら下地を差し替える。
- 下地がまだ何も描かれていないとき（いきなり高倍率で開いた場合など）に限り、低解像度版（`lowKey`）を優先度 0 で要求する。長辺 2048 の版は、上のルールのとおり後回しにする。

### 2. 詳細領域の余白を広げる

- `computeDetailRegion` の余白を、固定の 256px から「**表示領域の幅と高さの半分**（デバイス px）」に変える。
- 描画の固定費が大きく、描く範囲が広くなっても時間はあまり増えないためである（1536×1024 で 217ms に対し、512×512 で 170ms）。
- 画像が大きくなりすぎないよう、詳細領域の上限を 4096×4096 デバイス px とする。
- 単体テストを更新する。

### 3. 横スクロールが止まった後の遅延を減らす

- 見えている部分が今の詳細領域からはみ出したときの待ち時間を、100ms から **60ms** にする。
- スクロールが止まったことの判定（`pan-settle` の開始）は、今までどおり 100ms で行う。計測の条件は変えない。

### 4. ベンチマークの追加（`e2e/perf.spec.ts`）

- A1 の 400% の計測に、**すでに見えているページを拡大する場合**（DisplayList がキャッシュ済み）を明示的に含める。今の計測は、6ページ目を表示して `isSharp()` を待った後に拡大するので、そのままでよい。
- 加えて、拡大の直後に 250 CSS px 横へスクロールした場合の `pan-settle` を追加する（余白の範囲内なので、ほぼ 0 になるはず）。
- 実行するのは **Worker 3本・warm なし** の構成だけでよい（前回の結果で推奨された構成）。1〜2本は実行しない。
