# SPEC-01a-2: 長い描画の分割（途中で順番を譲れるようにする）

## 実行モデル指定（必須）

- モデル: `gpt-5.6-sol`
- reasoning effort: `high`
- 選定理由: 描画の要求の仕組み（PageView、RenderScheduler）の中核の改修と、不安定な計測の原因調査を含むため

---

## 目的

SPEC-01a の後のレビュー修正（コミット 789c954）で、次の3点を変えた。

- ページの担当 Worker を「最初の要求時に最も空いている Worker、以後固定」にした。
- DisplayList の見積もりを直した。
- ページ一覧の要求を、スクロールが止まった後にだけ出すようにした。

その結果、勢いよくスクロールしたときの白抜けは大きく改善した。しかし、次の2つが残った。

1. **A4 を 400% に拡大すると 1.09 秒かかる**（試作では 0.19 秒）。
   - 直前に拡大した A1 の「余白付きの詳細」（第2段）や「長辺 2048px の下地」が、同じ Worker で動いていることが原因である。重い図面では、これらの描画に 1.5〜2 秒かかる。
   - Worker は1回の描画を途中で止められないため、後から来た見えている範囲の要求（優先度 0）が待たされる。
2. **性能計測（`npm run bench`）で、`perf.spec` の後に続けて `perf-edit.spec` を実行すると、実施設計図の 12ページ目で `isSharp()` の待機が 180 秒でタイムアウトすることがある。** 単独で実行すると通る。

この SPEC では、**時間のかかる描画を細かい帯に分けて、帯と帯の間で優先度の高い要求に順番を譲れるようにする**。あわせて、2. の原因を突き止めて直す。

最初に `docs/第1版の計画.md`、SPEC-00a-2〜00a-4、SPEC-01a、`docs/調査/表示性能の測定.md`、今の `src/viewer/`、`src/client/` を読むこと。

## 対象

- 変更してよいファイル: `src/viewer/`、`src/client/`、`src/app/ThumbnailPanel.tsx`、`tests/`、`e2e/perf.spec.ts`、`e2e/perf-edit.spec.ts`
- 変更しないファイル: `src/core/`、`src/worker/`（帯の描画は、今の `render`（deviceRect 付き）でできる）、`docs/`、そのほかの設定

## 変更内容

1. **帯に分けた描画**（`src/viewer/bandedRender.ts` を新規に作る）
   - デバイス px で 1,000,000 画素を超える描画のうち、次の2つは、高さ 512 デバイス px 以下の横長の帯に分けて、帯ごとに別の要求として出す。
     - 第2段（余白付きの詳細）
     - 長辺 2048px の下地
   - 第1段（見えている範囲）は、速さを優先して分けない。
   - 帯は、届いた順に、その領域の大きさの canvas（1枚）の該当位置へ描き込む。すべての帯がそろった時点で、その領域を「完成」とする。
   - 鮮明さの判定（`isSharp()` と `regionCovers`）では、「見えている部分に重なる帯がすべて描かれているか」で判定する。
   - 帯のキャッシュの key には、帯の範囲を含める。
2. **順番の確認**: 帯に分けた後、A1 を拡大した直後に A4 を拡大したときの要求ログを記録する。A4 の見えている範囲の要求が、A1 の帯の要求を最大でも1つ待つだけで処理されていることを示す。
3. **不安定な計測の原因の調査と修正**
   - 失敗が再現するまで、`npx playwright test --project=bench` を繰り返す（最大5回）。
   - 失敗したときの状態（見えているページ、鮮明でないページの番号、描画の要求ログ、Worker ごとの待ち行列）を記録し、原因を突き止めて直す。
   - **待ち時間の上限を延ばすだけの修正はしない。**
   - 原因が計測の手順の側にある場合（例: 前のテストの Worker が残っている、ページの位置がずれる）は、手順を直してよい。その場合は理由を報告する。
