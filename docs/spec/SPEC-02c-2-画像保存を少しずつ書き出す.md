# SPEC-02c-2: 画像として保存を、ページごとにファイルへ書き出す方式に改める。あわせて、貼り付けのテストの失敗を直す

## 実行モデル指定（必須）

- モデル: `gpt-5.6-sol`
- reasoning effort: `high`
- 選定理由: SPEC-02c の続きで、同じスレッドで書き出しの方式を作り直すため

---

## 目的

SPEC-02c のレビューで、次の問題が見つかった。

1. **300 ページ（150 dpi・JPEG）の書き出しで、メモリが足りなくなる。**
   - 最後に出力の文書を `saveToBuffer` で一度に保存するとき、約 827MB の連続したメモリを確保できずに失敗した。
   - 終わりにまとめて保存する方式では、ページ数や解像度が増えると、また同じことが起きる。
2. **「保存の間だけ Worker 0 の元の文書を一時的に解放して、後で戻す」という対策は、採らない。**
   - 戻すのに失敗すると、利用者の開いている文書（未保存の書き込みを含む）が失われる危険がある。
   - その間に来た別の要求（描画・書き込みの反映）も失敗しうる。
3. **`e2e/copy-opacity.annotate.spec.ts` の「3件を別ページへ貼り付け、1回の元に戻すでまとめて消す」が、毎回失敗する。**
   - `Ctrl+V` の後、2ページ目の書き込みが3件増えるのを待つ所で、30 秒でタイムアウトする。
   - Claude Code が、SPEC-02c の変更を入れる前のコミット（`05c104f`。SPEC-02b-2 を公開した状態）でも実行し、同じく失敗することを確かめた。つまり SPEC-02b-2 からの問題である。

## 対象

- 変更してよいファイル: `src/core/rasterize.ts`、新規 `src/core/pdfStreamWriter.ts`、`src/worker/`、`src/client/PdfWorkerPool.ts`、`src/app/RasterizeDialog.tsx`、`src/App.tsx`、`src/editor/`（貼り付けの不具合の修正に必要な範囲）、`tests/`、`e2e/`
- 変更しないファイル: それ以外

## 変更内容

### 1. ページごとにファイルへ書き出す（`src/core/pdfStreamWriter.ts`）

MuPDF の出力文書を使わず、**画像だけの PDF を、自前でページごとに書き出す**。中身が「各ページに画像を1枚（または帯の画像を数枚）貼るだけ」なので、自前で書いても単純である。

1. ヘッダー（`%PDF-1.7` と、バイナリを示すコメント行）を書く。
2. ページごとに、次を書く。
   - 画像の XObject
     - JPEG は、`asJPEG` のバイト列をそのまま `/Filter /DCTDecode` のストリームにする（幅、高さ、`/ColorSpace /DeviceRGB` か `/DeviceGray`、`/BitsPerComponent 8`）。
     - 劣化なしは、`asPNG` の IDAT を連結して `/Filter /FlateDecode` と `/DecodeParms << /Predictor 15 /Colors n /BitsPerComponent 8 /Columns w >>` にする。PNG の IHDR で、幅・高さ・色の種類（グレー／RGB）・インターレースが無いことを確かめる。インターレースがあったら例外にする。
   - 内容ストリーム（`q 幅 0 0 高さ x y cm /Im0 Do Q`。帯のときは帯ごとに位置を変えて並べる）
   - Page オブジェクト（`/MediaBox`、`/Resources`、`/Contents`、`/Parent`）
3. 各オブジェクトを書いた位置（バイト位置）を覚えておく。
4. 最後に、Pages オブジェクト、Catalog、xref の表、trailer を書く。
   - Pages はページの数が最後まで分からないので、オブジェクト番号だけ先に決めて、最後に書く。
- 書き出し先は `FileSystemWritableFileStream`（`createWritable()` で開いたもの）に、ページごとに `write()` する。書き終えたら `close()`。
- **中止したとき、または途中で失敗したときは、`abort()` して、ファイルを書き残さない。**
- `showSaveFilePicker` が無いブラウザ向けには、ページごとのバイト列を `Blob` の部品として集め、最後に1つの `Blob` にしてダウンロードさせる（Blob は、ブラウザがメモリの外に持てる）。
- テスト用の窓口 `rasterizeToBytes(options)` は、同じ書き手を、メモリ上の書き出し先で使う（テストは小さい文書で行う）。

### 2. Worker の役割

- 描画用の Worker は、ページ（または帯）を描き、JPEG または PNG のバイト列を返す（今と同じ）。
- **Worker 0 は、出力の組み立てに関わらない。** 未反映の書き込みを反映した「別の文書（複製）」を、描画用の Worker に渡すところまでとする。
- **SPEC-02c で足した「Worker 0 の元の文書を一時的に解放する」処理は、取り除く。**
- main thread は、Worker から受け取ったページのバイト列を、すぐに書き手へ渡して捨てる。同時に持つのは、先読みの数ページ分（描画用の Worker の本数 × 2 まで）に限る。
- 複製の文書は、描画用の Worker で作り、書き出しが終わったら閉じる。

### 3. 貼り付けのテストの失敗を直す

- 失敗の原因を突き止める。例えば、次のどれなのかを見分けること。
  - `scrollToPage(1)` の後、「今見ているページ」が 1 ページ目と判定されていない。
  - 貼り付けの先のページが、読み込み（`ensurePageLoaded`）の前で、数に入っていない。
  - `Ctrl+V` のキーを受ける要素に、フォーカスが無い。
- **アプリの不具合なら、アプリを直す。** テストの手順の問題なら、利用者の操作に近い手順に直す。どちらだったかを報告する。
- 待ち時間を延ばすだけの修正はしない。

## テスト

- **単体テスト**（`pdfStreamWriter`）
  - 書き出した PDF を MuPDF で開けること、ページ数・大きさ・画像の色空間が合っていること。
  - JPEG と PNG（グレー・RGB）の両方。帯のページ。
  - 中止したら `abort()` が呼ばれ、`close()` が呼ばれないこと（書き出し先の偽物で確かめる）。
- **既存の画像保存のテスト**が、新しい方式でも通ること。
- **`npm run e2e` の全件**が成功すること（上の貼り付けのテストを含む）。
- **性能**（1回、失敗して直した場合は、直した後にもう1回まで）: `heavy-300p.pdf` の全 300 ページを 150 dpi・JPEG で書き出す。次を報告する。
  - かかった時間
  - 出力の大きさ
  - 書き出しの最中の main thread の JS ヒープの最大値（`performance.memory` が使えれば）
  - 途中で失敗しないこと

## 禁止事項

- 今開いている文書を変えないこと。Worker 0 の文書を解放しないこと。
- 中止・失敗のときに、書きかけのファイルを残さないこと。
- 対象外のファイルを変更しないこと。git の変更操作をしないこと。
- 自分で起動したサーバーは必ず止め、一時ファイルは削除すること。
