# SPEC-R4: 関連品目ルールの拡充・東京都の層・最適化

## 実行モデル指定（必須）

- モデル: `gpt-6.1-sol`（データの追加だけの回は `gpt-6-luna` / `max` に降格してよい。コードを変える回は sol-high）
- reasoning effort: `high`
- 選定理由: ルールの層の追加と性能の最適化はコードの判断を伴う。承認済みデータの追記だけなら定型作業。

---

## 目的

監査一覧で承認されたルールを段階的に足す。参考ルールの表示（既定は非表示）、東京都の運用の層、4工事区分・複合改修・撤去・解体の実例試験、性能の最適化を行う。

## 進め方（1回ごと）

1. 利用者が監査一覧（非公開の調査資料）の承認欄に「採用／要修正／対象外」を記入。
2. Claude が承認分を `src/core/related/rules.ts` に追記（品目キー・内訳位置の確定、分解、種別の見直しを含む）。ルールデータの版を上げる。
3. Codex は、データの追加に伴うコードの変更があるときだけ実装（例: 新しい文脈ルールの種類、都の層）。
4. 毎回: 単体試験（ルールごとの照合結果の固定試験を自動生成）、関係 e2e、`e2e/quantity-ui.perf.spec.ts`、`npm run audit:network`。

## 東京都の層

- `src/core/related/rules.tokyo.ts`（別ファイル）に、国のルールIDを指定して「採否・質問・根拠」を上書きするデータ。案件の設定で「国」「東京都」を選ぶ。都の照合が済むまで、都の案件でも国のルールを「参考」として表示。

## 性能の最適化（実測で必要な場合のみ）

- ルール数が数百件になったときの索引作り・照合の時間を `tests/storeBaseline.perf.test.ts` に追加して測る。登録1回の `related.suggest` の p95 が 20 ms を超えるなら、索引の分割・遅延を検討。

## 停止条件・禁止事項

- R1〜R3 と同じ。未承認の行を正式な提案として表示しない。参考ルールの表示は既定で非表示。
