# リポジトリの保護（2026-10-03）

第三者・連携アプリ・AI ツール・管理者本人の誤操作で、ソースコードや GitHub Pages の公開版が意図せず変わる危険を下げるための記録と手順。コードの変更は [SPEC-04a](../spec/SPEC-04a-リポジトリの保護.md)。

目指す形:

```
Claude Code / Codex / ローカル開発 → 作業ブランチ → Pull Request → CI（test-build）
  → 失敗: 直す / 成功: main へマージ → 自動では公開しない → 管理者が手動で Pages へ公開

main → fixed-release（手動）→ テスト・通信監査・ビルド → 固定版 ZIP / HTML 版 → SHA-256 を確認 → 職場の PC などへ配置
```

- **ソースを変えただけでは公開版は変わらない**（Pages は手動公開だけ）
- **固定版はファイルを取り替えない限り変わらない**

## 3. GitHub の画面で行う設定（管理者が行う）

順番が大事。**PR を作って CI（test-build）が一度動いてから** Ruleset を作り、その後に PR をマージする。

### 3-1. Ruleset で main を守る

1. リポジトリの **Settings → Rules → Rulesets → New ruleset → Import a ruleset** を押し、このフォルダの [`main-ruleset.json`](main-ruleset.json) を選ぶ
   - 手で作る場合: **New branch ruleset** で次のとおり
2. Ruleset name: `main を保護`、Enforcement status: **Active**
3. Bypass list: **空のまま**（Administrators、Repository admin、GitHub App、Deploy key を入れない）
4. Target branches: **Add target → Include by pattern → `main`**
5. Branch rules:
   - **Restrict deletions**: オン
   - **Block force pushes**: オン
   - **Require a pull request before merging**: オン。Required approvals: **0**（一人で運用するため。レビューする人ができたら 1 にする）
   - **Require status checks to pass**: オン → **Add checks** で `test-build` を選ぶ（source は GitHub Actions）。「Require branches to be up to date」はオフ
   - **Require signed commits**: **オフのまま**（6章）
6. **Create** を押す

確かめ方: ローカルで `main` に直接 push すると拒否される。PR の画面で test-build が通るまでマージボタンが押せない。

### 3-2. github-pages 環境（変更不要。確認だけ）

**Settings → Environments → github-pages** の Deployment branches and tags が **Selected branches and tags** で `main` だけになっている（調査済み）。任意で **Required reviewers** に自分を入れると、公開前にもう一度承認を求められる。

### 3-3. Actions の既定の権限

**Settings → Actions → General → Workflow permissions** を **Read repository contents and packages permissions** にし、**Allow GitHub Actions to create and approve pull requests** をオフにする。どのワークフローも権限を明示しているので、既定は読み取りだけで足りる。

### 3-4. 確認だけ行う項目（勝手に消さない）

| 場所 | 見ること |
|---|---|
| Settings → Collaborators | 自分以外に Write / Maintain / Admin の人がいないか |
| Settings → Deploy keys | 登録があれば Read-only か Write か。Write で心当たりの無いものは削除候補 |
| Settings → Secrets and variables → Actions | 名前だけ見る。今のワークフローは Secret を1つも使っていない。登録があれば削除候補 |
| GitHub の右上 → Settings → Applications → Installed GitHub Apps | 全リポジトリ（All repositories）が対象の App。karu-pdf だけで足りるなら **Only select repositories → karu-pdf** にする。ほかのリポジトリで使っていないか確かめてから |
| Settings → Code security | Dependabot alerts と Dependabot security updates をオンにする（任意） |

## 4. GitHub Pages へ公開する手順

1. 公開したいコミットが `main` にあり、その PR の test-build が通っていることを確かめる
2. **Actions → GitHub Pages へ公開 → Run workflow**、Branch は **main** のまま実行
3. 実行結果の要約（Summary）に出る「公開するコミット」が意図したものか確かめる
4. 公開後、`https://gibbon1116-ctrl.github.io/karu-pdf/` を開き、「新しい版があります」が出たら更新して動作を見る

`main` 以外を選んで実行しても build が飛ばされ、公開されない。

## 5. PWA の更新の動き（Pages 版）

- `registerType: 'prompt'` なので、新しい版を見つけても**勝手には切り替えない**。新しい Service Worker は取得後に待機し、アプリの上部に「新しい版があります。」と「更新する」が出る
- 「更新する」を押すと、書きかけの書き込みを確定し、未保存の文書があれば確認してから新しい版に切り替えて再読み込みする
- 押さない場合、旧版は**アプリの窓とタブをすべて閉じるまで**使われ続ける。すべて閉じて開き直すと、待機していた新しい版に切り替わる
- 新しい版の確認は、アプリを開いたとき（ページの読み込み時）だけ行う。定期的な確認はしない。オフラインのあいだは旧版がそのまま動く
- 古いキャッシュは新しい版が有効になったときに消える（`cleanupOutdatedCaches`）
- **インストールした PWA も Pages の更新に追従する。固定版ではない。** 職場などで固定して使うのは、固定版 ZIP か HTML 版（SHA-256 で確認したもの）

## 6. コミット署名（今回は有効にしない）

| 経路 | 今の状態 | 署名の見込み |
|---|---|---|
| ローカル Git（Claude Code が使う） | 署名の設定なし | SSH 鍵で署名できる（`gpg.format ssh`、`user.signingkey`、`commit.gpgsign true`、GitHub に Signing key として登録）。設定すれば Claude Code のコミットも署名される |
| Codex | git 操作をしない | 影響なし |
| GitHub の画面での編集・マージ | GitHub が自動で署名 | そのまま使える |

案: 「Require signed commits」を有効にするなら、先にローカルの SSH 署名を設定して数回試す。あるいはマージ方法を **Squash だけ**にすれば main に載るのは GitHub が作って署名したコミットになる（要検証）。どちらも運用が変わるため、別の作業として判断する。

## 7. CODEOWNERS

一人で管理している間は効果が小さいため追加しない。レビューする人が増えたら `.github/CODEOWNERS` に `* @gibbon1116-ctrl` と `/.github/ @gibbon1116-ctrl` を書き、Ruleset の「Require review from Code Owners」と Required approvals 1 を合わせて有効にする。

## 8. 残る危険

- 管理者のアカウントが乗っ取られると、Ruleset の解除や手動公開もできてしまう。二段階認証（パスキー）と、全リポジトリが対象の GitHub App の見直しが前提
- `actions/upload-pages-artifact` は内部で `actions/upload-artifact` をタグで呼ぶ。外側を SHA で固定しても、内側は固定されない
- 必須チェックは job 名 `test-build` で照合する。同じ名前の別のチェックで満たせる余地がある（Ruleset で source を GitHub Actions に限定して軽減）
- E2E（Edge を使う画面テスト）は時間がかかるため CI に入れていない。画面の不具合は手元の E2E で見る
- npm の依存は lockfile で固定しているが、`npm ci` は install script を実行する
- PWA の利用者は、Pages を公開した後に開いた時点で新しい版を受け取る（更新ボタンを押す、または窓をすべて閉じる）

## 9. 元に戻す

このブランチの変更はマージ後に `git revert <マージコミット>` で戻せる（PR の画面の Revert でも同じ）。履歴の書き換え（`reset --hard` と force push）は使わない。Ruleset は Settings → Rules → Rulesets で Enforcement を **Disabled** にすれば消さずに止められる。
