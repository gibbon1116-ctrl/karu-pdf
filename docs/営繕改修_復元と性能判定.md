# 営繕改修：復元と性能判定

2026-10-04の利用者指示により、数十ms程度の差は測定値を残して利用者の操作確認で採否を判断する。5%超過だけを理由に次の改修を止めない。今後の機能も同じ扱いとする。大きな遅延、フリーズ、破損、無制限なメモリ増加は引き続き修正する。

## 導入前へ戻す

導入前コミットは `130166f6049938814c1f1b7db124790593444f5a`。固定タグ `karu-pdf-before-eizen-20261003` と、ローカル `work/rollback/karu-pdf-before-eizen.bundle` に保存する。改修は `codex/eizen-review-upgrade` ブランチで行い、機能ごとのコミットで戻せるようにする。

改修作業を残したまま導入前版を別フォルダへ復元する例：

```powershell
git worktree add --detach ../karu-pdf-before-eizen karu-pdf-before-eizen-20261003
Set-Location ../karu-pdf-before-eizen
npm.cmd ci
npm.cmd run build
```

元のGitデータが失われた場合は bundle を `git clone work/rollback/karu-pdf-before-eizen.bundle <復元先>` で読み、上記タグをチェックアウトする。作業中のフォルダで `reset --hard` を実行する必要はない。

PDF原本は改修前版とは別の資産。試用ではコピーを開き、別名保存する。アプリの旧版へ戻すだけでは、保存済みPDFの内容は戻らない。

機能単位で意味のある単体・画面・保存再読込テストを行う。性能差は絶対ms、相対%、条件、測定していない項目を区別し、利用者確認前の小差を合格・不合格と断定しない。基本操作の大きな悪化を確認した場合は機能を簡略化する。
