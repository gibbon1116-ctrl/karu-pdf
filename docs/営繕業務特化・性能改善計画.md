**通常閲覧の性能を維持する。** 2026-10-04の利用者指示により、数十ms程度の差は記録し、採否は利用者の操作確認で判断する。5％超過だけを理由に次工程を止めない。導入前タグ・bundleと機能ごとのコミットを保存する。詳細は [復元と性能判定](営繕改修_復元と性能判定.md) を参照。大きな遅延やメモリ増加、破損は修正し、必要なら機能を簡略化する。

今回は既存コード・試験・公式API資料を調査したうえでの計画作成まで。アプリの実装、依存関係の更新、公開、Driveへの書き込みは行っていない。機能の現状はコードで確認したもので、今回ブラウザで動作検証した結果ではない。

ローカルHEADと、調査時点のGitHub `main` は同じコミットだった。実装開始時にHEADと作業ツリーの変更を再確認する。基準コミットを更新する場合は性能基準も再取得し、異なる版の結果を混ぜない。

### Worker・キャッシュ・配布形態

- 通常は端末の論理コア数に応じて3本または4本のPDF Workerを使う。文書処理の主Workerと描画Workerを分け、プール全体の上限は4本。別に画像処理Workerの経路がある。
- `StructuredTextCache` はページ単位で、既定の保持上限は20ページ。本文抽出のための全ページ常駐キャッシュは作らない。
- `DisplayListCache` の既定上限は96MiBの推定値。通常ビューのBitmapキャッシュは512MiB、warm用は64MiB、比較用は96MiB。これは設定上限であり、実使用量やアプリ全体のメモリ上限ではない。
- 2画面用にもキャッシュがあり、複数ビューでは上限が積み上がる。文書データ・WASM・画素バッファを含めて実測し、3画面の可否を判断する。
- 多くの画面機能は `App.tsx` から静的にimportされている。新機能を使わないときの初期読込量も検査する。
- 通常版、固定・閉域版、単一HTML版がある。コード分割は単一HTMLの組立方法と整合させる。追加の実行時通信・外部フォント取得を要求しない。
- 新機能のためにWorker数を文書数に比例して増やさない。既存プールで不足する場合だけ、オンデマンド解析Workerを比較検証する。

Driveでは関連フォルダと固定版配布ZIPを確認した。基準測定用の実図面は今回特定・取得していない。配布物の内容を、現在のGitHubソースと同一とは判断していない。

## 3. 改修前性能の取得を最初の必須工程にする

### 現時点での測定状況

既存の `npm run bench`、表示・注釈・比較・計測・2画面の性能試験がある。`src/perf/metrics.ts` にはopen、鮮明表示、描画、ズーム確定、パン確定、白抜けの記録がある。

ただし今回の作業ツリーには `node_modules/`、`test-data/`、`bench-results/` がない。**今回のコミットでの性能測定は未実施で、5％条件の合否は未判定。** 計画作成の段階では依存関係のインストールや試験PDFの生成を行わない。

過去の `docs/調査/表示性能の測定.md` にはSPEC-00a-4時点・Worker3本で初ページ1.4秒等の記録がある。現在の実装とは条件が異なるため、参考資料にとどめ、今回の基準値には採用しない。

### 第0段階の手順

1. 基準コミット、lockfile、ビルドモード、Node・ブラウザ・OS・CPU・RAM・電源・画面解像度・DPR・Worker数を記録する。
2. `npm ci` でlockfileどおりに準備し、現行版の単体試験とビルドを確認する。依存更新は別の変更として扱う。
3. `npm run make-test-pdf` で既存の重い試験PDFを作成する。実図面は所在・対象ページ・SHA-256を確認してローカルの試験領域へ用意する。
4. 現行コードのまま既存性能試験を実行し、足りない測定項目は共通の試験ハーネスで補う。その同じ測定方法を基準版と改修版の双方に適用する。
5. 生データと環境情報を `bench-results/eizen/<基準SHA>/<実行日時>/` に保存する。機密図面・抽出本文・生ログをGitに追加しない。共有用の要約だけを `docs/調査/` に保存する。

既存openの計測開始はファイルの `arrayBuffer()` より後にある。ファイル読込を含む「利用者が開く操作を確定してから」の時間を別途測り、既存値と混同しない。

### 試験データ

| データ | 主に確認すること |

| 小さな通常PDF | 開く・ページ移動・文字入力・保存・機能未使用時の負荷 |
| 既存の約97MB・300ページ生成PDF | 大容量読込、スクロール、メモリ、A1の高倍率描画 |

| 人工的に変更・余白・ページ順・回転を変えた新旧PDF | 差分・位置補正・ページ対応・引継ぎの正否 |

過去資料にある実図面のURLは、取得時に到達性とPDFの同一性を確認する。8GB程度の想定端末でも代表ケースを確認し、試験端末がない場合は未検証として残す。

## 4. 測定項目と性能の合否

| 項目 | 測定する区間・値 |
|---|---|
| PDFを開く時間 | ファイル選択確定／ドロップ受理→文書が操作可能。ファイル取得、バイト読込、Workerでのopenも内訳を記録 |
| 最初のページ | 同じ起点→ページ画像の初表示、さらに鮮明表示。復元位置が先頭でない場合は別ケース |
| 読込への反応 | 操作受理→待機表示の描画。まず100ms以内を設計目標とし実機で確認 |
| スクロール | 既存の1500／3000px/s、cold／cached、フレーム時間p95、白抜け率・最長時間 |
| ズーム・パン | A1/A4の100→400％、操作→可視領域の鮮明表示、フレーム時間p95 |
| 注釈入力 | 描き始め、追従、確定、移動、多数注釈時の応答とフレーム時間 |
| 文字入力 | 日本語IME・長文・確定時の応答。既存の追加文字と、新しい本文修正を別計測 |
| ページ移動 | ページ指定／次ページ→対象ページの初表示・鮮明表示 |
| 保存 | 操作→PDF生成完了とファイル書込み完了。増分・完全保存、再openも確認 |
| メモリ | 読込前・読込後・操作中ピーク・解析中・機能終了後・文書終了後。JS、Worker/WASM、画像・キャッシュ、ブラウザプロセスを区別 |
| 初期読込量 | cold時の実転送量とJS/WASM/フォント等の内訳。単一HTMLはファイルサイズ・起動時展開時間とメモリも記録 |

### 判定ルール

- 同一端末・ブラウザ版・ビルドモード・PDF・Worker数・操作列で比較する。coldとwarmを分離し、片方だけのキャッシュ済み状態を比較しない。
- 開く等の経過時間は各条件でまず5回以上測定し、中央値とばらつきを記録する。フレーム時間p95は十分なフレーム数から計算する。少数の反復から安定した経過時間p95を得たとは扱わない。
- 値が小さく5％差を分離できない場合、またはばらつきが大きい場合はA/B交互実行・反復追加で再判定する。判別できないものは「測定不足」とし、合格扱いにしない。
- 時間・読込量等の差率は `(改修後 / 改修前 - 1) × 100`。通常操作は5％以内を必須条件とする。**最初の基準版と直前の合格版の双方に比較し、段階ごとの小さな悪化を累積させない。**
- 白抜けや停止は割合だけで判断しない。基準が0の場合は相対差を使わず、新たな継続的白抜け・長い停止がないことを確認する。
- 通常閲覧時のメモリと初期読込量も5％以内を開発上の目標とする。機能使用中の追加メモリは別に予算を決め、閉じた後に解放されることを確認する。GPU・WASMを含まない値を総メモリと呼ばない。
- 新機能の実行中も閲覧・注釈操作を併走して測定する。5％を超える場合は処理を小分けにし、閲覧操作中は解析を休止する。それでも重い場合は対象ページ・解像度・件数を制限する。
- 5％を超えた項目は原因の記録→改善→同条件で再測定する。未修正・未測定を残したまま次の機能を完成扱いにしない。

メモリの `performance.memory` はメインスレッドのJSヒープに限られる。`measureUserAgentSpecificMemory()` は利用可能性とsecure context・cross-origin isolationに制約があるため、通常版・固定版・単一HTMLで当然に使えるとは扱わない。利用できなければ同じ条件のブラウザプロセス測定とキャッシュ統計等を併用し、測れない領域を明記する。[MDNの仕様説明](https://developer.mozilla.org/en-US/docs/Web/API/Performance/measureUserAgentSpecificMemory)

## 5. 機能ごとの実装案

### A. PDFを開く直後の待機表示

- ファイル選択でファイルが確定した時点、ドロップ受理、最近使ったファイル・OS起動経路での読込開始時点から、軽量なステータス表示を出す。
- 「PDFを開いています」→「ページを表示しています」の段階表示を基本とする。実際に測れるファイル数・処理済みページ数だけ進捗に使い、推測の％は表示しない。
- `openQueueRef` と連携して複数ファイルの待機を扱う。成功、失敗、重複文書への切替、上限到達、取消の各経路で確実に終了する。
- 全画面の重いダイアログや高頻度タイマーを作らず、既存ステータス欄等を使う。表示が実際に描画されることと、初ページ表示を遅くしないことを試験する。

### B. 図面内文字の抽出・出力

- 既存の構造化文字解析を再利用し、「現在ページ／選択ページ／全ページ」を利用者が明示して実行する。OCRは初期対象外。
- まず文字列、ファイル名、1始まりのページ番号、行ID、ページ上の位置・範囲をCSVとUTF-8テキストに出す。CSVは既存のBOM・改行・引用・表計算の数式誤認対策を再利用する。
- 位置はMuPDFページ座標を基準に、左上原点・pt/mm・ページ寸法・回転を定義する。必要なら正規化座標も出す。CropBox・UserUnit・回転を試験する。
- 図面番号は利用者指定または指定した図枠範囲からの候補抽出とする。一般的な図面番号を自動で正しく判定できるとは約束しない。
- 重複文字、縦書き、回転文字、読み順、ToUnicode不足は品質上の制約として記録する。文字がないページと、抽出に失敗したページを区別する。
- Workerでページごとに処理して結果を小分けに渡す。上限付きキャッシュ、結果の逐次書出し、取消、保存との排他を用意する。全ページのStructuredTextや巨大JSONをメインスレッドに常駐させない。
- キャッシュは文書・ページ・解析オプション・本文世代で識別し、編集・ページ整理で無効化する。再実行でも無制限に結果を積み上げない。

文字と座標の取得はMuPDF 1.28.1の `StructuredText.walk()` 等で確認できる。これは抽出の根拠であり、本文を書き換えられることの証明ではない。[StructuredText公式資料](https://mupdf.readthedocs.io/en/1.28.1/reference/javascript/types/StructuredText.html)

### C. 既存PDF本文の文字修正

本実装前に、実際のnpm版MuPDF 1.28.1の型定義・実装・日本語PDFで小さな検証を行う。文字抽出結果だけでは、元の命令・フォント符号・共有リソースを安全に書き換えられるとは判断しない。

| 方式 | 採用条件・扱い |
|---|---|
| 元の本文命令を置換 | 元オブジェクトとの対応・フォント符号化・幅・共有範囲を確定できる限定構造だけ検証。難しければ初期版では見送る |
| 選択文字だけ除去して再配置 | 文字だけを除去し図形・画像・近接文字を保護できるケースで検証。元フォントの再利用可否と代替フォントを明示する |
| 訂正注釈 | 本文修正が安全でない場合の代替。元本文が残ることを利用者に示し、「本文編集できた」と報告しない |

- 「文字修正」モードを選んだ後、対象ページ・選択範囲だけ解析する。通常openで編集可能性を全ページ判定しない。
- 選択→編集→プレビュー→確定を基本とし、領域や文字幅の違いを確認できるようにする。読み取れない文字、画像文字、共有Form XObject、複雑なクリッピング等は対象外にできる。
- 署名・編集制限は既存の安全判定を維持する。原本への自動上書きを前提にせず、初期版は別名保存を基本にする。
- 本文を変更する処理は失敗時に元の状態へ戻せる作業用コピー／トランザクションで行い、Undoと保存・再openを検証する。表示・文字解析・描画Workerの該当世代を更新する。
- 除去方式は全文保存と再抽出で旧文字が残らないことも確認する。白い矩形で隠しただけの状態を本文の削除・置換と呼ばない。
- 既存 `safeOutput.ts` は別用途の安全出力であり、その処理を本文編集へそのまま流用しない。既存のRedaction注釈を意図せず適用しないことも検証する。
- 近接する寸法線・図形・文字の消失、対象外ページの変更、日本語欠落があればその方式は不採用。対応可能範囲を狭くして提供する。

公式資料の `PDFPage.process()` には「only mutool run」の注記がある。ブラウザ版で使えると仮定しない。`applyRedactions()` は内容を恒久的に除去するAPIのため、対象・オプション・復元方法を確認する。[PDFPage公式資料](https://mupdf.readthedocs.io/en/1.28.1/reference/javascript/types/PDFPage.html)

### D. 指摘管理の拡張

- 現行のマーク・一覧・CSV・Undoを拡張する。別の指摘システムは作らない。
- 安定した指摘ID、番号、内容、ページ・位置、分野、回答、状態、修正確認を扱う。状態は「未回答→回答済→修正済→確認済」を基本とし、差戻しも手動でできる。
- PDF注釈の既存カスタム情報をバージョン付きで拡張し、PDF保存・再openで往復できるようにする。番号の振り直しでも関連付けが変わらないよう、IDと番号を分ける。
- 旧 `open/done` を読めるようにする。旧「対応済」を自動で「確認済」とみなさず、旧状態を保持して移行を促す。古いアプリで新しい項目を再保存した場合の制約も確認する。
- 全文書の一覧・集計はパネルを開いたとき、または明示実行時に読み込む。ページ・状態・分野の絞り込みと多数行の仮想化を検証する。

### E. 個数カウント

- クリックで印を追加し、種類・ページ・文書ごとに集計する。種類は照明・コンセント等の利用者指定とし、機器の自動認識は導入しない。
- 安定ID・種類・ページ・位置を保存し、誤クリックの取消、削除、種類変更、Undo、保存・再open、CSVを用意する。
- 既存注釈層を基盤に、可視ページ・範囲だけ表示する。多数時は描画の集約や位置索引を検証し、点ごとの重いDOM・イベントを増やさない。
- 集計は変更点だけ反映する。個数入力のたび全ページを読み直さない。1,000／5,000個の負荷試験から実用上限と必要な簡略表示を決める。

### F. 新旧比較と建築・電気・機械の重ね合わせ

- 既存の比較・2画面同期・差分一覧・平行移動を土台にする。
- 2文書の透過率、表示切替、必要なら分野別の色分けを追加する。透過率の変更でPDF解析を繰り返さず、上限付きの表示画像から合成する。
- 手動のページ対応表を作り、ページ順や余白の違いを扱う。図面番号は対応候補の根拠として使い、利用者が確認する。
- 位置合わせは既存の平行移動を改善して先に提供する。次に基準点2組による回転・均等拡縮を検証し、必要性と負荷が合う場合だけ追加する。自動全ページ位置合わせ、非線形変形は初期対象外。
- 補正は表示上の変換として持ち、原本PDFを勝手に変形しない。補正後の差分位置・注釈位置を原本ページ座標に変換できるようにする。
- 差分は現在の組・必要な表示領域だけ処理する。対話中の低解像度表示、操作後の詳細化、取消とキャッシュ解放を維持する。
- 建築×電気等は用途・表示名を整え、同じ2文書基盤を利用する。常時3文書を重ねる前提にしない。

### G. 前回指摘の引継ぎ

- 指摘ID、版を識別する文書情報、図面番号、確認済みページ対応、原本座標と補正変換を使う。ページ番号だけで対応を確定しない。
- 未解決指摘の候補位置を新版に仮表示し、「対応確定／要確認／対応先なし」を示す。利用者が確認したものだけ新版の指摘として保存する。
- ページ挿入・削除・同番号の複数図面・回転・縮尺変更・補正範囲外を試験する。曖昧な対応を黙って採用しない。
- 元版・元指摘との関連を残し、繰返し実行で二重登録しない。取消とUndoを用意する。
- 引継ぎだけで「修正済／確認済」と自動判定しない。修正確認は比較画面と回答を見て利用者が行う。

### H. 変更管理

- 図面上のマークと、変更ID・内容・理由・関連指摘ID・状態を結び付ける。必要に応じてCSVへ出す。
- 指摘のデータ・一覧・選択連携を再利用し、関連IDの破損や孤立をチェックする。
- 工程表、予算、人員管理、承認ワークフロー、クラウド共同編集へ拡張しない。

### I. 複数図面の効率的な比較

- 既存2画面で、設計図・施工図・総合図・機器承諾図の参照先と対応ページを切り替えやすくする。開く文書数と同時描画する文書数を分ける。
- 非表示タブの描画・解析を停止し、文書数に比例して高解像度画像・Workerを増やさない。
- 3画面は最後に独立した検証を行う。キャッシュの全体予算、画面面積、描画優先度を測り、通常操作が基準を満たす場合だけ追加する。満たさなければ2画面＋参照切替に限定する。

## 6. 共通の性能設計

1. **新機能を呼び出すまで処理を開始しない。** open時に全ページ文字解析・差分・指摘対応付けを追加しない。メニュー表示だけで解析を開始しない。
2. 解析は既存Worker構成を優先し、可視描画・入力を先に処理する。長い同期MuPDF呼出しは途中取消できるとは仮定せず、ページ・処理段階の境界で中断する。単一ページでも応答を阻害する場合は解析用Workerとの比較を行う。
3. 文書ID・要求ID・世代を付け、タブ切替・終了後の古い結果を破棄する。表示変更だけで同じPDFを再解析しない。
4. キャッシュはページ数だけでなくバイト数も管理し、比較・抽出・引継ぎの終了時に一時資源を解放する。全ページの高解像度画像を保持しない。
5. 大量一覧は仮想化し、可視ページの注釈だけ描画する。大量データのコピー・巨大JSON・React再描画を避ける。
6. 新機能を共通open経路へ載せない。大きな追加モジュールは配布形態に合う遅延読込を検証する。単一HTMLの互換性のための変更は別工程で性能を確認する。
7. 保存・本文修正・ページ整理と読取解析の競合を制御する。完全保存、Workerの再読込、署名制限等の既存処理を迂回しない。

各段階を「小さな実装→機能試験→性能比較→合否記録」で閉じる。機能ごとに変更を分け、前の段階が不合格なら次の追加を始めない。

| 3 | 指摘の分野・回答・状態・修正確認 | 旧形式の移行、保存・再open、一覧連携、多数指摘時の性能合格 |

## 8. 試験の実行範囲

- 各機能では該当する単体・結合・E2Eを先に行い、次に既存の表示・入力性能試験を実行する。
- 文字抽出は期待文字・件数・位置を原本と照合し、CSVをExcel等で確認する。文字修正は表示画像と再抽出の両方で検証する。
- 注釈・指摘・カウント・変更記録は保存→再openで内容・ID・状態・座標を確認する。Undo、取消、読込失敗、Worker失敗、タブ切替を含める。
- 比較は人工的な正解データで差分・ページ対応・補正を確認し、実図面で細線と日本語が失われないことを確認する。
- ページ整理・既存注釈・フォーム・検索・保存・2画面の既存試験を維持する。共通保存・Worker・座標処理を変更したときは関連範囲まで広げる。
- 通常版を中心に性能比較し、固定版・単一HTML版でも読込・編集・保存・新機能と通信制約を確認する。単一HTMLの起動性能も比較する。
- 新機能未使用、実行中、終了直後の3状態を区別し、終了後に解析要求・Worker処理・メモリが残らないか確認する。
