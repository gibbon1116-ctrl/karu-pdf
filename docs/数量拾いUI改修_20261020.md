## 数量拾いの初回表示

原因は、道具の切替処理が全ページの注釈を読み終えるまでパネルを開かず、
各ページの読込ごとに全体の変更状態と画面を再計算していたこと。
枠と読込中表示を先に開き、全ページの読込通知をまとめる。
全ページの読込、旧形式の個数印の復元、準備完了前の編集禁止は維持する。
読込中に別の道具へ切り替えた場合、完了後に数量拾いへ戻さない。
通常閲覧の1ページ単位の読込・通知は従来どおり。

### 性能の参考値

Linuxの同一実行環境・Chromium・本番ビルド・1440×900・Workers 2・warm 0。
Service Workerを無効にした新しいブラウザーコンテキストで、100ページ、
各100個の円注釈（合計10,000件）の合成PDFを使用。
PDFの先頭ページ表示後、数量拾いボタンのクリックから測定する。
表示はパネルDOMの出現、準備完了は追加ボタン有効化後の次フレーム。

| 指標 | 改修前中央値 | 改修後中央値 | 差 | 相対差 |
| --- | ---: | ---: | ---: | ---: |
| 枠の出現 | 9,413.1 ms | 411.9 ms | −9,001.2 ms | −95.6% |
| 操作準備完了 | 9,432.5 ms | 573.7 ms | −8,858.8 ms | −93.9% |

改修前5回のうち開発用チェックと近接した初回・最終回を除いた3回、改修後5回の中央値。
変更状態の再計算回数は103回から6回へ減少（起動・PDF読込を含むカウンター）。
再現用: プレビュー起動後 `node scripts/bench-quantity-opening.mjs`。
ブラウザー実行ファイルは必要に応じ `KARU_BROWSER_PATH` を指定する。
読み込む注釈数自体は減らしていないため、最終的な文書保持メモリ量は同程度。

単体テスト47件・読込を意図的に停止する画面テスト2件・ビルド成功。
単体テストは一括通知、部分失敗後の再試行、リセット、通常の即時通知、
既存の数量・ページ・変更状態の整合性を確認。

実際の利用者の図面、Windows／Edge、ネットワーク配信、通常閲覧の広範な性能と
最大メモリ量は未測定。上記の比率をすべての図面の保証値とはしない。
