# かるPDF 要件と設計方針

2026-09-27 に、ユーザーと合意して決めた内容をまとめる。以後の SPEC はすべてこの文書を前提にする。

## 1. 目的

動作の重い既存の文書ソフトの代わりになる、軽い PDF 編集アプリを作る。

既存のソフトで不満だった点は次の3つで、これを解消することを目標にする。

- ページ送りと拡大縮小が遅い
- 書き込みの反応が遅い
- 一度書き込んで保存した文字を、後から編集できない（**必ず解消する**）

## 2. 配布と利用

| 項目 | 決定 |
|---|---|
| 形態 | ブラウザだけで動く Web アプリ。GitHub Pages で配信する |
| URL | `https://gibbon1116-ctrl.github.io/karu-pdf/` |
| アプリ名 | かるPDF |
| リポジトリ | 個人アカウント `gibbon1116-ctrl` の公開リポジトリ `karu-pdf` |
| データの扱い | PDF はパソコンの中だけで処理する。外部へは一切送信しない |
| 利用者 | 数人〜数十人の小さなチーム |
| 対応ブラウザ | Edge、Chrome の最新版だけ（File System Access API を使うため） |
| オフライン | PWA にする。初回表示後はネットなしで動く。Edge の「アプリとしてインストール」に対応する |
| 外部読み込み | しない。WASM・フォント・CMap などはすべて GitHub Pages 上に置く |
| 画面の言語 | すべて日本語 |
| ライセンス | アプリ全体を AGPL-3.0-or-later で公開する（MuPDF.js を使うため）。BIZ UD フォントの OFL ライセンス文も同梱する |

想定する利用環境で満たすべき条件は次のとおり。

- ソフトをインストールしなくても使えること（ブラウザだけで動く）
- Edge と Chrome で動くこと
- 書類を外部のサーバーへ送らないこと
- 将来 GitHub Pages が使えなくなったときに、インストール不要の exe 版へ移せる余地を残す

## 3. 機能と作る順番

| 段階 | 内容 |
|---|---|
| 試作 | 性能と、日本語の書き込みを保存して再編集できるかを確かめる（第7章） |
| 第1版 | ページ操作（結合・分割・抽出・削除・並べ替え・回転・白紙挿入）、書き込み（文字・線・矢印・四角・丸・蛍光ペン・手書き）、白塗り |
| 第2版 | ページ番号・ヘッダー・フッター、画像→PDF と PDF→画像、軽量化、付箋コメント |
| 第3版 | 透かし、フォーム入力、本当の墨消し（下層のデータも削除する）。しおりの編集は、利用者の指示で作らない（2026-09-30） |
| 作らない | 押印、パスワードの設定と解除、既存の文字の直接書き換え、Word・Excel→PDF、OCR、PDF 以外の独自形式の文書 |

作らない理由は次のとおり。

- **既存の文字の直接書き換え**: 白塗りと文字の追加で代わりが利く。
- **Word・Excel→PDF**: Office の「PDF として保存」で代わりが利く。
- **OCR**: 重く、目的と矛盾する。
- **PDF 以外の独自形式**: 元のソフトで PDF にしてから開く。

## 4. 書き込みと保存

- 書き込みは **PDF の標準注釈として保存する**（FreeText、Line、Square、Circle、Highlight、Ink など）。何度開き直しても再編集できるようにする。
- 提出用に **「確定して別名で保存」** を用意する。注釈をページに焼き付け、後から編集できない状態にする。
- Acrobat など他のソフトで付けた標準注釈も編集できるようにする。
- 作成者名は記録しない。
- 書体は **BIZ UDゴシック** と **BIZ UD明朝**（OFL）。アプリに同梱し、保存時は使った文字だけを PDF に埋め込む。FreeText の外観（AP）は、この書体を埋め込んだ状態で自前で生成する。
- 初期設定は、色が赤、線の太さが 1pt、文字が BIZ UDゴシックの 10.5pt。最後に使った設定を次回に引き継ぐ。
- 上書き保存（Ctrl+S）は、開いた元のファイルへ File System Access API で直接書き込む。別名保存は Ctrl+Shift+S。
- 自動保存はしない。機密の書類をブラウザの中に残さないため。
- 保存せずに閉じようとしたら警告を出す。
- 元に戻す（Ctrl+Z）とやり直し（Ctrl+Y）を用意する。

## 5. 画面

```
┌─[ファイルA.pdf]─[ファイルB.pdf]─[＋]──────────────┐  ← タブで複数ファイル
│ 開く 保存 │ 選択 文字 線 矢印 □ ○ 蛍光ペン 手書き 付箋 白塗り │  ← ツールバー
├──────┬──────────────────────────┬───────┤
│ ページ │                                │ 書式    │
│ 一覧   │        PDF本体（表示・編集）      │ 色/太さ │
│（縮小）│                                │ 文字サイズ│
├──────┴──────────────────────────┴───────┤
│ 「ページ整理」画面へ切替: 全ページを並べて表示。         │
│  ドラッグで並べ替え、他のPDFをドロップして結合、         │
│  範囲を選んで削除・回転・抽出・分割                    │
└──────────────────────────────────────────┘
```

- 表示は連続スクロールを基本にし、見開きにも切り替えられる。Ctrl＋マウスホイールで拡大縮小する。
- 最近使ったファイルの一覧を付ける。記録するのはファイル名と場所（ファイルハンドル）だけで、中身は保存しない。
- 印刷は、編集結果を Edge・Chrome 標準の PDF 表示で開き、そこから印刷する。
- 新しい版を公開したら「新しい版があります」と表示し、クリックで更新する。
- 使い方の説明は、アプリ内の「使い方」ページと README に書く。
- ページ番号の初期設定は下中央の「- 1 -」。開始番号・位置・書式は変更できる（第2版）。

## 6. 技術構成

| 項目 | 決定 |
|---|---|
| PDF エンジン | **MuPDF.js**（npm `mupdf`、Artifex 公式、AGPL-3.0） |
| 実行場所 | MuPDF.js は Web Worker で動かし、画面のスレッドを止めない |
| 拡大表示 | 見えている範囲だけをタイルに分けて描く |
| 土台 | TypeScript、Vite、React |
| テスト | Vitest（単体）、Playwright（画面の操作） |
| 実装の分担 | Claude Code が SPEC を作ってレビューし、Codex（`gpt-5.6-sol`／`high`、MCP 経由）が実装する |

MuPDF.js を選んだ理由と、他の候補との比較は [調査/PDFエンジン比較.md](調査/PDFエンジン比較.md) に記録した。

試作での実測では、PDFium は拡大表示の描画が 5〜10 倍速かった。しかし、埋め込まれていない日本語フォントを表示できなかった。そのため MuPDF のまま進め、描画の部分は後から差し替えられる形にしておく（2026-09-28。詳しくは [調査/表示性能の測定.md](調査/表示性能の測定.md)）。

表示は Worker 3 本で行う。要求は `RenderScheduler` で一元管理し、1ページの要求はすべて同じ Worker（ページ番号 % Worker 数）が受け持つ。高い倍率では、見えている範囲 → 余白付きの範囲の順に、二段階で描く。

## 7. 性能目標と試作の合格基準

想定する利用者のPCは、メモリ 8GB・数年前の Core i5 相当とする。

試作は、300 ページ・100MB・A1 図面入りの PDF（公開されている官公庁の設計図書で代用する）で、次の5項目を満たすかを確かめる。

1. 開いてから1ページ目が表示されるまで3秒以内
2. スクロールしたとき、次のページが白く抜けない
3. A1 図面を 400% に拡大したとき、0.5 秒以内に鮮明な表示が追いつく
4. 文字の入力や図形のドラッグで、遅れを感じない
5. 日本語の書き込みを保存し、開き直して再編集できる。同じ書き込みが Edge と Acrobat Reader で同じ見た目に表示される

不合格の項目があれば、EmbedPDF（PDFium）と比べてから決め直す。

### 試作の結果（2026-09-28）

| 基準 | 結果 | 判定 |
|---|---|---|
| ① 開く | 1.4 秒（300 ページ・97MB） | ✅ |
| ② スクロール | 普通の速さでは白抜け 0〜4.5%。速いスクロールでは、灰色の仮表示が 0.1〜0.2 秒出る | ✅（速いときは △） |
| ③ 400% 拡大 | 実物の図面で最大 0.44 秒、A4 で 0.19 秒。わざと極端に重くした試験用 A1 では 0.83 秒 | ✅（利用者のPCで要確認） |
| ④ 書き込みの反応 | ドラッグ p95 16.8ms（最大 17.3ms）、文字入力 p95 13ms（重い図面の 400% 表示の上で測った） | ✅ |
| ⑤ 日本語の書き込みの保存と再編集 | 保存 → 開き直す → 書き直すができた。回転ページでもできた。Edge と同じエンジン（PDFium）でも、Acrobat でも、同じ見た目になった | ✅ |

- 開発機（Ryzen 5 5625U）で測った。利用者のPCでの最終確認が残っている。
- 実装は SPEC-00a〜00b-3。

## 8. 動作確認

- 性能は、こちら側で、公開されている官公庁の設計図書を使って測る。測定結果は [調査/表示性能の測定.md](調査/表示性能の測定.md) に記録した。
- 最終確認は、利用者が実際の書類を使って行う。
- 他のソフトで書き込みをした実際の書類は、試験には使わない。既存のソフトとの互換性は、利用者が実際の環境で確認する。
