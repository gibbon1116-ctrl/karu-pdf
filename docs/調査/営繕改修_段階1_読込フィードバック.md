# 営繕改修・段階1：PDF読込への即時反応

2026-10-03。基準コミット `130166f6049938814c1f1b7db124790593444f5a`。本書は段階1当時の実装・測定記録。段階2v4では内部段階の変化に伴う同期更新を省き、表示を「PDFを開いています」に統一した。最新版の性能判定は段階2の記録を参照。

## 結果

PDFを選択・ドロップした直後から「PDFを開いています」を表示し、文書の準備後は「ページを表示しています」に切り替える。初ページの画像が届いたら終了する。正確な進捗を取得していないため、％表示はしない。

ファイル読取失敗、壊れたPDF、Worker初期化失敗、初描画失敗、0ページ、8文書の上限、重複文書への切替でも待機表示を解除する。複数ファイルは従来のキューで順に開き、別文書の遅い完了が現在の待機表示を消さないよう要求IDと文書IDで判定する。

待機表示は専用コンポーネントだけを更新する。使用していない間のタイマー、全ページ解析、文字解析、追加Worker、Canvasは増やしていない。

通常版の測定範囲では、操作全体の中央値の悪化が5％以内。これは全改修の完了報告ではなく、段階1の記録である。

## 環境と方法

- Windows 10.0.26300、Ryzen 5 5625U、12論理CPU、物理RAM約16GB、Edge 154.0.4258.53、Node 24.18.0。
- 1440×900、DPR 1、Worker 4、先読み無効、Service Worker無効。試行ごとに新規ブラウザコンテキストを作成。OSキャッシュ・他アプリは制御していない。
- `sample-small.pdf`：5ページ・3,476 bytes。`heavy-300p.pdf`：約97MB・300ページ、250ページの画像と50ページの密なA1ベクトル図。6ページ目のA1を400％に拡大してパンする。
- 操作試験は各PDF・各版5回。描画操作をrequestAnimationFrame起点に揃え、日本語文字入力は試行ごとに200回。フレームp95は各試行内の多数フレームから算出し、表はその5試行の中央値。
- 読込の追加試験は各PDF・各版7回。改修前後をAB/BA順で交互に実行し、ファイル読取とWorker応答を外部ハーネスで観測した。通常コードに計測機能は追加していない。
- ブラウザプロセスのprivate bytesは、テストが起動したブラウザのPIDだけを集計した定点値。Worker/WASMも含むプロセスの割当量であり、GPUのVRAMや真のピークを測った値ではない。メインJSヒープは別に記録した。

基準distと候補distは `bench-results/eizen/baseline-dist` と `open-feedback-v2-dist` に保存した。再実行手順は `scripts/eizen-bench.mjs`、集計は `scripts/eizen-compare.mjs`。数値と全試行サンプルの要約は [結果JSON](./eizen-open-feedback-results.json) に保存した。

## 性能比較

読込はAB/BA追加試験の中央値。旧測定で「文書操作可能」と呼んだ値は、読取・全Workerのopen・ページ情報が揃い、内部の文書一覧へ登録されたことをRAFで観測した値だった。ReactのタブDOM反映より前に検出される場合があり、画面が操作可能になった時点を保証する名称ではなかった。段階2v4からは内部登録と実際のタブDOM反映を別々に記録し、条件の異なる旧値を新測定へ合算しない。

### 読込内訳（診断値）

| 区間 | 通常 改修前→後 | 大容量 改修前→後 |
|---|---:|---:|
| File.arrayBuffer 呼出し→解決 | 1.7→5.2 ms | 145.2→153.3 ms |
| primary WorkerのMuPDF open | 8.7→10.3 ms | 82.3→87.3 ms |
| primary Workerのページ情報取得 | 15.1→17.1 ms | 24.6→22.6 ms |

各区間の中央値は加算して全体時間にしない。Workerは複数並走する。Fileの計測はPromiseがメインスレッドへ戻るまでの時間を含み、待機UIの描画やOSスケジューリングも混ざる。内部の短い区間を相対5％以内と判定したものではない。通常PDFの読取Promiseの差は3.5msで、文書操作可能までの差4.8msに含まれる。内訳の差は残して、利用者の操作全体で5％以内か判断した。

## テストと実図面

- 単体：55ファイル・321件合格（RenderSchedulerの失敗・遅い応答に関する2件を追加）。
- 新規読込E2E：8ケース合格。読取前の表示、複数キュー、ハンドル取得、ドロップの同期取得、読取/形式/Worker/描画失敗、0ページ、上限、重複を確認。
- 通常版の既存smoke・注釈・保存再読込E2Eも合格。
- 固定配布版：build・通信監査・16 E2E合格。単一HTML版：build・通信監査・20 E2E合格。オフラインと通信制限も従来の試験で確認。
- [七ヶ浜町の公開図面PDF](https://www.shichigahama.com/benricho/oshirase/documents/c70-1140d.pdf)（23,787,521 bytes・30ページ、A3 27枚/A1 3枚）を取得し、A1の21ページ目で400％拡大・パン、スクロール、注釈・文字入力・保存を1回確認した。これは機能確認であり、5％の性能判定には使わない。

## 改善履歴と残る課題

最初の実装はAppの状態で待機表示を更新しており、通常PDFの初表示が7.00％、鮮明表示が5.28％遅くなったため不採用。専用store/コンポーネントに分離した。短いページ移動と入力の測定開始位相も見直し、修正版を基準版と同じハーネスで測り直した。旧失敗結果は `comparison-open-feedback-v1.json` に保存した。

未測定・未判定として、8GB端末、真の操作中ピーク、GPU VRAM、実ユーザーによるIME変換、ファイル指定先への実ディスク上書き時間、固定/単一HTMLの改修前後5回以上の性能比較が残る。ダウンロード完了観測は記録しているが、実上書き時間の代用にしない。固定/単一HTMLは機能互換を確認した範囲である。

既存のA1/A4混在文書では、A1拡大後にA4へ移動すると横位置が画面外に残る場合がある。今回の注釈測定では対象ページのoffsetLeftへ横位置を合わせた。待機表示の追加で発生した問題ではなく、別の表示修正候補として保持する。
