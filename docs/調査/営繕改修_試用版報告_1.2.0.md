# 営繕改修 試用版 1.2.0（2026-10-04）

試用版 1.1.0 の機能を、利用者の指摘を受けて実務の使い方に合わせて作り直した版。指摘は次の2点だった。

- 個数カウントは、図形を登録して照明器具やコンセントの種類ごとに数えられないと使えない。
- 指摘と変更記録が通し番号で混ざり、扱いが分かりにくい。

決めたことと経緯は [実用性レビュー](../営繕改修_実用性レビュー.md)。1.1.0 の記録は [試用版報告 1.1.0](営繕改修_試用版報告.md)。性能差の採否は、これまでと同じく利用者の操作確認で決める（数十ms程度の差だけで工程を止めない）。

## 個数カウント（器具リスト）

- 左の「器具」タブで器具を登録する。名称・略号・分類と、印の形（14種類）・塗り（5種類）・色（24色）・大きさ・透明度を決める。形・塗り・色はすべて図形で選ぶ。
- 「見本から追加」に、建築・電気設備・機械設備の一般的な器具がある。まとめて登録できる。
- 登録済みの器具を「複製」し、名称・略号・形などを変えて追加できる。追加・複製・見本から追加の初期値には、使っている数の少ない形・塗り・色の組合せが入る。「別の組合せを提案」で次の候補に替わる。14種類を超えると、どの形もすでに使われているので、使われ方の少ない形・塗り・色の組合せになる。
- 器具の追加・編集で「図面から見本を切り取る」を押し、図面の記号を四角で囲むと、その部分の図面（書き込みは含まない）が器具の見本になる。器具リストの行に小さく表示し、マウスを載せると拡大する。見本は表示用で、図面から記号を自動で探す機能は作っていない（利用者の判断）。
- 器具の行を選んで図面をクリックすると、その器具の印が付く。行には表示中の図面と全図面の個数を出す。
- 目の印で、器具や分類ごとに図面上の印を出し入れできる。「選択中の器具だけ表示」で絞れる。
- 「個数をCSVに書き出す」で数量表を作る。ページごとの列と合計を出し、0個の器具も含める。
- 器具リストは PDF の中に保存する。別のタブで開いた PDF から器具を読み込める。
- 1.1.0 で種類名を付けて数えた PDF は、器具タブを開くと種類ごとの器具に移る。

実際の図面（`test-data/shichigahama-drawing.pdf` の天井伏図）で、凡例の「天井カセット型空調機」の記号を切り取って器具にした（`work/walkthrough-04f.mjs`、画面は `work/screens-04f/`）。マウスを離してから見本が出るまで 883ms、見本は 160×120 画素・base64 で 2,140 文字、その後の保存は 81ms だった。

## 1.1.0 で作った PDF との互換

試用版 1.1.0 で作った PDF（`test-data/real/legacy-trial-1.1.0.pdf`。指摘2件・変更記録1件・個数カウント5個）を 1.2.0 のビルドで開いた（`work/check-legacy-trial-pdf.mjs --new-issue`、記録は `work/legacy-check-1.2.0-candidate.log`）。

- すべての書き込みを読み込み、開いただけでは未保存の印が付かない。
- 指摘の CSV に旧版の指摘2件（番号1と3）が出る。旧版の変更記録は「変更記録（旧版）」として一覧に出る。
- 新しく指摘を置くと番号4になる（文書全体の通し番号の続き）。

## 性能

### 多数の印の保存（ブラウザー、`work/measure-5000-save.mjs`）

器具リストの導入で、旧形式の個数カウントを器具の印へ移す保存や、印の多い器具の書式変更の保存が、件数の2乗で遅くなっていた。原因は2つあった。印ごとに呼んでいた MuPDF の `annotation.update()` と、失敗したときに元へ戻すための MuPDF のジャーナルである。前者は自前の外観を `setAppearance` で入れるように変え（SPEC-04j）、後者は50件ごとに操作を区切るように変えた（SPEC-04k）。失敗したときに全部を元へ戻す性質は保っている。

| 場面 | 直す前 | 1.2.0 |
|---|---:|---:|
| 旧形式の印1,000個の移行と1器具の書式変更 | 50,234ms | 614ms |
| 　同じく印5,000個 | 25分を超えた | 2,199ms |
| 1器具の書式変更（印1,000個中10個） | 214ms | 181ms |
| 　同じく印5,000個中50個 | — | 779ms |
| 1個追加（印1,000個の文書） | 202ms | 210ms |
| 　同じく印5,000個の文書 | — | 939ms |

印5,000個の文書では、1個追加しただけの保存でも1秒近くかかる。内訳は測っていないが、保存した文書を開き直して確かめる処理など、文書全体の注釈の数に比例する処理があるためとみている。

## 未測定・残課題

- 四角・線・丸・手書き・文字など、個数カウントと指摘以外の書き込みの外観は、今も MuPDF の `update()` で作る。1ページに数千個あると、件数の2乗で遅くなる（Node で四角2,000個の作成と更新に約24秒）。照査で1ページにこの数を描くことは考えにくいので、今回は直していない。
- 印5,000個の合成PDFを開いて操作できるまで約20秒かかる。1.1.0 の試験でも 20.7〜22.0秒で、今回の改修で増えたものではない。内訳は測っていない。
- 利用者の実図面（電灯コンセント平面図など）での個数カウント、実際のIME入力、上書き保存のディスクI/O、8GB端末は未確認。
- 引継ぎのまとめ表示とページ対応のPDF内保存は、1.2.0 の試用後に決める（実用性レビューの順8）。

利用者の試用では、まず PDF を開く、拡大・スクロール・パン、文字の入力と保存を確かめ、その後に器具リスト・指摘・CSV を確かめる。性能差の採否は実際の操作の感覚で判断する。
